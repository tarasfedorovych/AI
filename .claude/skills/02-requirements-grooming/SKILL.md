# Requirements Grooming

Analyzes requirements from the context file from QA grooming perspective,
finds issues, coordinates with the user, and creates a final numbered list
of requirements — input for the next skills.

## Input Data

Input — context file `<ISSUEKEY>-context.md` created by
01-task-context, read from the story folder.

## Story Folder

All inputs and outputs live in the story folder built by
01-task-context:

```
stories/**/{ISSUEKEY}/
```

Locate it by globbing `stories/**/{ISSUEKEY}/` — one glob matches both
`stories/{EPIC-KEY}/{ISSUEKEY}/` and
`stories/{EPIC-KEY}/{FEATURE-KEY}/{ISSUEKEY}/`.

If the folder does not exist, or it holds no `{ISSUEKEY}-context.md` —
stop and tell the user to run 01-task-context first. Do not create the
structure here, and do not fall back to the working directory.

Data sources for this skill:
- context file (source of truth)
- attachments referenced in the context file, if needed
  for understanding the requirements
- user responses to grooming questions

Do not go to the tracker, do not use external tools,
do not search the internet. Context file — only source of truth.

Context file — read-only. Do not change, do not rewrite,
do not clear its contents.

If the context file is corrupted, duplicated, or internally
contradictory — stop and inform the user that the context needs to be
regenerated by the context collection skill.

## Rules

- All communication and all output file content — in English.
- Chat messages — brief.
- Analyze only what is in the context file. Do not guess,
  do not supplement, do not interpret requirements on your own.
- Do not turn ambiguity into fact.
- Preserve the original meaning of requirements during analysis.
  Do not improve, do not rephrase, do not simplify wording
  on your own. A requirement can be rewritten only after
  agreement with the user.
- Related tracker context — background only. Do not create findings
  just because a related task has different wording
  or additional requirements.
- Do not generate findings artificially. If a requirement is clear and covered —
  it is covered.
- After saving the file — stop. Do not continue to checklist,
  test cases, or planning.

## Requirements Numbering

Assign each item from the "Requirements" section of the context file
a sequential ID: REQ-1, REQ-2, REQ-3...

Numbering is sequential, without gaps, in the order the items
appear in the context file.

If during grooming a requirement contains several different things —
split into sub-items: REQ-5a, REQ-5b. The main number
is preserved, sub-items are added.

These IDs are permanent — they do not change during the work
of all subsequent skills in the chain. REQ-5 in the grooming file —
is the same REQ-5 in the checklist, in code review, and beyond.

## Grooming Method

For each requirement from the context file, go through four questions:

1. **Can I verify this?**
   Is there enough specificity: expected result, screen,
   state, condition, trigger. If not — requirement is not covered.

2. **What do I need for this?**
   Is it clear what data, access, role, system state are needed.
   If unclear from context — clarification question.

3. **Where can this break?**
   Check through the lens of test design:
   - Boundary values: is it described what's at the boundary and beyond
   - States and transitions: are all states described, all valid
     and invalid transitions between them
   - Condition combinations: if there are several conditions (role + status +
     data state), is behavior described for each combination
   - User classes: is behavior divided for different
     roles, account types, access levels
   - Negative scenarios: what if data is empty, deleted,
     in invalid state, action is cancelled
   - Parallel actions: what if state changed while user
     is on the page

4. **What is not written?**
   - Alternative and exceptional scenarios (main flow exists,
     but what if something goes wrong?)
   - Dependencies between features: does a change affect other flows
   - Contradictions between requirements in the context file

Broad or vague wording — signal to check deeper.
Examples: "where applicable", "all places", "update wording",
"appropriate messages", "handle", "support".

### Application Rules

- Each requirement goes through all 4 questions, but record
  the result only where the question is relevant. Do not generate
  problems artificially for simple or unambiguous requirements.
- After checking individual requirements — check related groups:
  requirements that describe one flow, one screen, or one feature.
  At the joints between related requirements there may be gaps
  not visible when checking each separately.
- If several requirements describe variants of one behavior —
  check if all variants are covered, including those
  not explicitly written (negative, alternative, exceptional).
- Write only what really affects implementation,
  testing or task acceptance. A question that won't change
  either code, test, or acceptance result — do not write it.
- Do not generate questions about:
  - implementation details that the developer decides (architecture,
    libraries, cache, performance) if not written
    as a requirement in the requirements
  - standard browser or platform behavior
    (opening tab, scroll, focus)
  - UX details that don't affect functionality
    (animations, timings) if not written in requirements
  - general infrastructure (server errors, timeouts,
    retries, logging, network failures) if the ticket
    is not specifically about it
  - things obvious from task or product context —
    do not re-ask what is already clear

## Workflow Order

1. Read the context file completely.
2. If something is unclear about the product, feature, or task context
   — ask the user before starting grooming.
   Do not start grooming until you understand the context.
   Do not ask about obvious things and about things that do not affect
   grooming requirements.
3. After receiving answers — start grooming requirements.
4. Number all requirements: REQ-1, REQ-2...REQ-N.
5. Groom each requirement through the grooming method.
6. In chat, write only problematic requirements, grouped
   by categories: questions, contradictions, potential bugs,
   uncovered requirements, risks. One REQ can appear
   in several categories. Each problem — briefly:
   essence of the problem and what is needed to solve it.
   Covered requirements — do not mention.

   Format in chat:

   ### Questions
   - REQ-3: <problem essence> → <what is needed to solve>

   ### Contradictions
   - REQ-5: <essence> → <what is needed>

   ### Potential Bugs
   - REQ-7: <essence> → <what is needed>

   ### Uncovered Requirements
   - REQ-9: <essence> → <what is needed>

   ### Risks
   - REQ-7: <essence> → <what is needed>

   Empty categories — do not write.
7. Wait for user responses, coordinate solutions.
   If user cannot answer or says skip —
   leave the requirement as is without changes.
8. Form final list: covered requirements without changes +
   problematic requirements rewritten considering agreements.
   Copy the "Goal" section from the context file without changes —
   it is needed by the next skills to understand the context.
9. Save one file — clean numbered list
   of ready requirements.

## Output File

Create file `<ISSUEKEY>-requirements.md` in the story folder,
beside `<ISSUEKEY>-context.md`:

```
stories/**/{ISSUEKEY}/{ISSUEKEY}-requirements.md
```

The next skill reads it from the same folder.

If the file already exists — delete it completely and create a new one.

Template — in references/output-template.md.

## Final Response

After saving the file, inform the user of the path to the saved file.
